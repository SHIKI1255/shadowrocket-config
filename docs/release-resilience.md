# 自动发布异常处理（第一阶段）

正常发布必须通过现有数量、格式、冲突、路由、离线复现等全部检查；这些门槛未放宽。
DNS、UDP、Hosts、节点和手机导入地址没有改变。Hosts 本机任务保持独立。

## 有限重试与留证

公开 GET 对超时、连接中断、临时 DNS 错误、HTTP 429/500/502/503/504 最多尝试 3 次。
通常等待 2、8 秒；Retry-After 最多等待 60 秒。认证、404、TLS、格式或哈希失败不当作临时网络错误。
发布、提交、创建 PR 等写请求不自动重试。

公共生产仓库的 public-evidence 构建附件保留 7 天，含已成功下载的公开快照、固定来源版本、
逐文件哈希、结构化差异、数量变化及审核建议。下载中断时明确标为不完整。
无法解析时仍尽力生成原始文本差异；差异超过 2000 行会标明截断，完整候选快照仍保留。
早于下载的单元测试或运行器故障可能没有源快照，不能把缺少快照当成成功。
证据目录与可发布目录分离，证据没有发布所需的 SHA256SUMS 或配置清单。

## 人工确认的数量候选

仅公共生产仓库生成候选。只有已知数量门槛失败、其余解析/冲突/路由预检查通过，
且源码与前一发布仍未推进时，才创建 review/upstream-<指纹> 草稿 PR。
PR 只写 reviews/upstream/ 下的报告、源状态、拟议基线和说明；不修改 shared/baseline.json。
不能把合并报告视作同意放宽数量门槛。

人工核对完整新增、删除、顺序、源身份及覆盖范围后，明确确认需要接受的变化。
随后将拟议精确迁移应用到生效基线，补充回归测试，重新完成所有联网/离线和发布验证。
若上游、基线或代码已变化，必须重做审核；未知语义、冲突和路由回归不生成可放行提案。
同一指纹只产生一份候选；已有或已关闭的 PR 不重复创建，不强推，不自动批准或合并。
候选由 GITHUB_TOKEN 创建，事件不保证自动执行所有 PR 检查；人工应用后必须检查完整验证实际运行，
必要时手动触发 main 上的验证。候选报告本身不具备发布资格。

## 每小时消费与通知

公共生产及小火箭保持北京时间 06:17；QX 每小时第 47 分、Clash 每小时第 17 分检查公共版本。
GitHub 排队可能延迟。公共版本相同且本地构建代码未变、没有待恢复告警时，跳过重复构建。
有变化时锁定公共 release 提交 SHA，再执行全部验证；不执行下载的代码。
源码 push、PR 和普通手动运行仍完整验证；手动 probe_only 用来验收小时检查路径。
本地应用的资源刷新频率不因此改变。

每仓库用一条带机器标记的 GitHub issue 记录当前异常；相同错误指纹不重复写入或评论。
新原因更新一次；完整验证、发布及匿名下载哈希通过后关闭一次。无变化检查不能冒充恢复。
通知能否到达取决于 GitHub 订阅/通知设置。新候选 PR 只创建一次；不另建 Codex 定时任务。
只有受信任 main 任务有 issue/候选写权限，PR 没有写权限；默认仓库令牌权限保持只读。
公共生产仓库需允许 Actions 创建 PR；即使平台设置同时允许审核，程序也不调用审核/合并接口。

## 发布验收与回退

每次正式发布后匿名核对固定提交及滚动 release 的全部文件哈希。
滚动地址缓存不一致最多再检查 2 次（5、15 秒）；仍不一致则报警，不重复提交或自动回滚。
发布后读回失败不意味着 release 没有推进，处理时先核对实际 ref。
旧 release 和审核输入均有固定提交；需要回退时由使用者明确选择旧版本，按原回放流程完整验证发布。
本阶段不自动接受上游变化，不保证设备连接效果，也不保证零人工维护。
